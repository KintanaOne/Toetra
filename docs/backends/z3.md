# Z3 Backend

> Status: Planned / first strategic backend candidate  
> Scope: SMT-style backend query generation and execution  
> Priority: P1

## Purpose

The Z3 backend is intended to provide symbolic verification capabilities for FORML queries.

Z3 is a natural first backend for FORML because it can represent logical constraints, numeric comparisons, boolean structure, and satisfiability/counterexample-oriented workflows.

This document defines the target architecture for Z3 integration.

## Role in FORML

The Z3 backend should consume a backend-specific query produced after the logical pipeline:

```text
SemanticValidatedAST
→ IR1 / NNF
→ IR2 / CNF-DNF
→ AggregatedAssertionSet
→ LoweredQuery
→ Z3Query
→ Z3 execution
→ VerificationResult
```

Z3 should not consume AST nodes directly.

## Candidate use cases

The Z3 backend is especially relevant for:

| Use case | Why Z3 helps |
|---|---|
| Bound checking | Numeric inequalities can be encoded symbolically. |
| Monotonicity constraints | Counterexample search can be formulated as satisfiability. |
| Logical consistency | CNF/NNF constraints can be checked. |
| Local robustness abstractions | Neighborhood constraints may be encoded symbolically for simple models. |
| Counterexample generation | Z3 can produce satisfying assignments when a negated property is satisfiable. |

## Input expectations

The Z3 backend should receive a lowered query where:

- variables are explicit;
- feature references are resolved;
- comparison operators are normalized;
- boolean structure is normalized;
- model constraints are explicit;
- unsupported high-level problem predicates have been lowered or rejected.

## Initial Arithmetic Encoding Profile

The initial Z3 path should recursively encode scalar IR expressions.

Initial supported profile:

- numeric constants;
- resolved numeric feature references;
- numeric model-output references;
- unary numeric signs;
- addition and subtraction;
- multiplication by a numeric constant;
- division by a non-zero numeric constant;
- comparisons between the resulting expressions.

Examples:

```forml
2 * x0.a + x0.b <= target
(target - x0.baseline) / 2 >= 0
```

Nonlinear products and symbolic denominators must be declared as separate requirements and rejected by capability routing until explicitly supported:

```forml
x0.a * x0.b <= 5
x0.a / x0.b <= 2
```

The backend must not silently approximate these forms. Domain arithmetic bounds use the same recursive scalar translator but are emitted with `DOMAIN` provenance before the final verification condition is assembled.

## Potential Z3 artifacts

Future artifacts may include:

```python
@dataclass(frozen=True)
class Z3Query:
    declarations: list[Any]
    constraints: list[Any]
    objective: str | None
    metadata: dict[str, Any]
```

Or a more backend-agnostic intermediate:

```text
BackendQuery(kind="z3", payload=...)
```

The exact implementation can evolve, but the boundary should remain explicit.

## Property encoding strategy

Many verification properties are checked by searching for a counterexample.

Example pattern:

```text
To verify property P:
    check satisfiability of NOT(P)

If SAT:
    counterexample exists
If UNSAT:
    property holds under encoded constraints
If UNKNOWN:
    verification inconclusive
```

This pattern should be documented and made explicit in result diagnostics.

## Relationship with IR1 and IR2

IR1 provides a normalized logical tree with negation handling and NNF-oriented structure.

IR2 may provide CNF or DNF depending on the verification strategy.

Z3 may not always require strict CNF, but IR2 remains useful for:

- canonicalization;
- simplification;
- case splitting;
- tracing;
- minimizing assertions;
- deterministic backend query generation.

## Model encoding

Z3 integration depends heavily on model encoding.

A simple model may be encoded directly:

| Model family | Possible status |
|---|---|
| Linear regression | Candidate for direct symbolic encoding. |
| Logistic regression | Candidate with care around nonlinear/logistic transformation. |
| Decision tree | Candidate through path constraints. |
| Random forest | Possible but more complex. |
| XGBoost | Possible but requires tree ensemble encoding. |
| Neural network | Usually requires specialized encoding or another backend. |

The ModelBridge should provide schema and metadata. A future model encoder should transform model structure into Z3-compatible constraints.

## Capability declaration

A Z3 capability declaration should describe:

- supported property types;
- supported model families;
- supported data types;
- supported numeric operations;
- affine arithmetic support;
- nonlinear arithmetic support;
- symbolic-division support;
- support for counterexamples;
- timeout handling;
- exactness assumptions;
- unsupported constructs.

## Result model

Z3 results should be normalized into FORML results.

| Z3 outcome | FORML result |
|---|---|
| UNSAT on negated property | verified |
| SAT on negated property | violated with counterexample |
| UNKNOWN | inconclusive |
| timeout | failed or inconclusive with diagnostic |
| encoding error | backend compilation failure |

## Diagnostics

The Z3 backend should produce diagnostics such as:

```text
Property verified: no counterexample exists under the encoded constraints.
```

```text
Property violated: Z3 found an assignment satisfying the negated property.
```

```text
Query unsupported: feature 'color' has categorical dtype but no categorical encoding was provided.
```

## Miova testing opportunities

Miova can challenge Z3 integration by mutating:

- comparison operators;
- numeric bounds;
- variable declarations;
- logical forms;
- model constraints;
- backend query payloads;
- timeout options.

Expected failures must be explicit and classified.

## Non-goals for initial Z3 support

Initial Z3 support should not attempt to support every ML model family.

The first useful version may focus on:

- simple numeric and affine arithmetic constraints;
- bounded properties;
- logical properties;
- simple symbolic model encodings;
- counterexample generation.
