# Toetra 1.0.0rc4

`1.0.0rc4` makes the complete Toetra command-line and automation surface
available for evaluation. It keeps the formal verification profile introduced
by the earlier candidates while adding a process interface designed for local
use, CI jobs, and MLOps orchestration.

## Status and availability

This version is an evaluation release candidate, not the stable `1.0.0`
release. It is currently installed from a source checkout or source archive and
is not published on PyPI.

The candidate is intended for public observation of installation, command-line
behavior, artifact production, diagnostics, and supported verification routes.
A soundness, security, provenance, installation, or reproducibility defect may
still require another release candidate.

Follow [Installation and availability](../getting-started/installation.md), then
inspect both installed entry points:

```bash
toetra --version
python -m toetra --help
```

## Complete CLI surface

Both entry points expose the same five commands:

- `toetra init` creates a model-aware starter specification and validates it
  before atomic publication;
- `toetra validate` checks syntax, semantic validity, or executable readiness
  without solving;
- `toetra inspect` returns the resolved executable plan without exposing private
  compiler IR or backend formulas;
- `toetra verify` executes the existing verification runtime and emits text,
  exact JSON v6, or HTML output;
- `toetra replay` checks archived counterexample or witness evidence against
  concrete artifacts without silently rerunning formal verification.

The process contract distinguishes positive conclusions (`0`), formal failure
or replay inconsistency (`1`), inconclusive results (`2`), and invalid process
usage or inputs (`3`). Primary outputs and optional artifacts are written
atomically, and successful artifact runs finish with a versioned
`toetra.run-manifest` completion marker.

## Declared and effective execution context

A specification may declare default model, target, and dataset values. Explicit
Python or CLI values override those declarations for one invocation without
rewriting the source policy. Validation, inspection, JSON v6 reports, manifests,
and replay preserve both the declared and effective execution context.

The optional `dataset := ...` declaration is now propagated through parsing,
semantic compilation, artifact resolution, provenance, validation, inspection,
and replay. Information-bearing DSL arguments must be preserved until their
owning boundary or rejected explicitly rather than being discarded silently.

## Repository and release hardening

Since `1.0.0rc3`, the repository also gained reproducible outside-in CLI smoke
coverage, anonymous public-surface checks, controlled-exposure procedures,
stronger public collaboration gates, explicit third-party dataset provenance,
and PolyForm Noncommercial 1.0.0 licensing with a separate commercial route.

## Compatibility

`1.0.0rc4` does not widen the formal model or backend profile:

- fitted single-output sklearn `LinearRegression`;
- direct fitted binary sklearn `LogisticRegression`;
- finite transformed numeric features;
- affine semantic lowering and Z3 execution;
- text, HTML, Jupyter, records/DataFrame, JSON v6, provenance, and concrete
  replay.

The public Python facade remains limited to the same nine names. JSON reporting
remains schema v6. No serialized private compiler IR or stable plugin API is
introduced by the CLI.

## Release gates

The candidate is accepted only when CI, documentation and repository contracts,
the cross-platform CLI smoke scenario, reproducible wheel/sdist construction,
clean-wheel installation, demos, outside-in rehearsal, and review-bundle
reproducibility are green.
